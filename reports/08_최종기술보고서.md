## 2. 모델 학습 결과 — [산출물 1](01_FineTuning_결과보고서.md)

| 항목 | A. Head-only (필수, 서비스 사용) | B. Full Fine-tuning (선택 실험) |
|---|---|---|
| 학습 대상 | 분류 헤드만 (Backbone 고정) | 전체 가중치 |
| lr / epochs / batch | 0.0002 / 3 / 8 | 0.00005 / 3 / 8 |
| Train / Validation 수 | 1,034 / 133 | 1,034 / 133 (같은 분할) |
| **Best Validation Accuracy** | **0.7669** (102/133, epoch 2) | **0.9699** (129/133, epoch 1) |
| Test 성능 | 미측정 | **0.9531** (122/128, 1회, 추가 스크립트) |
| 모델 파일 | `artifacts/beans_resnet18/model.safetensors` | `artifacts/beans_resnet18_full/model.safetensors` |

- 데이터 점검: Split 사이 같은 이미지(MD5) 0건, 이미지가 아닌 파일 1개는 학습에서 자동 제외됨, 비슷한 사진(dHash) Split 간 거리 5 이하 0쌍.
- B가 A보다 **20.3%p(0.2030)** 높았다. 단, 학습 대상과 학습률 두 가지가 같이 바뀐 비교다.
- B를 Validation으로 최종 선택한 뒤 Test를 1회 평가했다: Accuracy 0.9531, Macro F1 0.9533, 병든 잎 놓침 0장. 가장 약한 지점은 bean_rust → angular 혼동 4장이다.
- 원본 기록: `artifacts/*/training_report.json`, `reports/evidence/train_log_*.txt`

## 3. 아키텍처와 데이터 흐름 — [산출물 2](02_시스템_아키텍처.md)

- 동기: 브라우저 → FastAPI → Redis DB/1 캐시 → (MISS면) ResNet18 → JSON 200
- 비동기: 브라우저 → FastAPI → `media/jobs` 저장 + PostgreSQL `queued` → Redis DB/2 → Celery Worker → 캐시 또는 ResNet18 → PostgreSQL `done` → 상태 조회
- 모델은 **FastAPI와 Worker 프로세스에 각각 따로 로드**된다. 캐시는 두 경로가 함께 쓴다 (실측으로 확인).

## 4. API·DB 설계 — [산출물 3](03_API_명세서.md) / [산출물 4](04_DB_구조_작업이력.md)

- API 4개(`/health`, 동기 분류, 비동기 접수, 상태 조회)와 화면 2개. 실제 응답으로 200·202·400·413·404를 확인했다. 503은 미실시.
- DB: `image_jobs` 한 테이블(12컬럼, PK `id`, `status` 인덱스). 비동기 작업만 기록하고 이미지는 파일로 따로 저장한다.
- 상태 전이 `queued → running → done`은 실제로 모두 관찰했다. `failed`는 미발생.

## 5. 버튼 처리 검증 — [산출물 5](05_AI버튼_처리흐름.md)

- 동기: 결과가 HTTP 응답 안에 들어 있다 (200, 31~34ms).
- 비동기: 202로 접수(job_id)만 받고, 폴링으로 완료를 확인한다. Worker가 꺼져 있으면 `queued`로 기다리다가, 다시 켜면 바로 처리됐다.

## 6. 실제 성능 비교 — [산출물 6](06_성능비교_보고서.md)

| 항목 (5회 중앙값) | 값 |
|---|---:|
| 동기 MISS HTTP (결과 포함) | 20.2 ms |
| 동기 HIT HTTP | 1.5 ms |
| 비동기 MISS HTTP (접수) | 12.3 ms |
| 비동기 MISS 최종 확인 (0.2초 폴링 포함) | 221.7 ms |
| 모델 추론 (동기 MISS) | 16.18 ms |
| Worker 첫 모델 로딩이 포함된 추론 | 2,624 ~ 3,059 ms |

- 비동기는 **접수 응답이 39.1% 빨랐다.** 하지만 결과를 받기까지는 **201.5ms 더 느렸다.** 추론이 빨라진 게 아니라 접수와 처리를 나눈 효과다.
- 캐시 HIT은 동기 응답 시간을 92.6% 줄였다. HIT의 `inference_ms=null`은 추론 생략이라는 뜻이다.
- 실제로 개선할 점: 모델 로딩이 첫 요청의 `inference_ms`에 섞인다. 서버를 시작할 때 모델을 미리 불러오면(warm-up) 첫 요청 지연을 줄일 수 있다. **제안만 했고 미구현**이다.

## 7. 기능 테스트와 오류 조치 — [산출물 7](07_기능테스트_오류분석.md)

- 실환경 테스트 14건 PASS, 2건 미실시(503 브로커 장애, Worker 내부 실패). 모의 pytest(가짜 모델)도 PC에서 4 passed였지만, 실환경 결과와 따로 구분했다.
- 실제 겪은 오류 8건을 기록했다 (Python 버전, 데이터 폴더 겹침, Docker 미실행, 가상환경·폴더 혼동, 캐시 재요청 혼동, 콜드스타트, 로그 덮어쓰기 등).
- 관찰한 오분류: `bean_rust_test.10` → angular, `healthy_test.10` → bean_rust. 확신도가 낮은 정답: `angular_leaf_spot_test.0` (0.46).

## 8. 성능 향상 방안 (교과 9 OpenCV·ML)

### 8-1. 실제로 해 본 것
| 실험 | 구현 | 데이터 / 평가 조건 | Validation Accuracy | 결론 |
|---|---|---|---:|---|
| E0: Head-only ResNet18 | ✅ 실행 | Validation 133장 | 0.7669 | 기준선 |
| E1: Full Fine-tuning | ✅ 실행 | 같은 Validation 133장 (+ Test 1회 0.9531) | 0.9699 | **20.3%p 상승** (학습 대상·lr 동시 변경) |
| E2: CNN + HSV 규칙 | ❌ 미구현 | 설계만 | 미측정 | 효과 미검증 |
| E3: CNN + ML 융합 | ❌ 미구현 | 설계만 | 미측정 | 효과 미검증 |

### 8-2. 제안 — OpenCV 병반 특징 + 규칙 보류 [제안 / 미구현]

```text
입력 이미지 → RGB→HSV → 잎 마스크(녹색 구간 inRange) → 마스크 안에서 황색·갈색 병반 후보 inRange
→ Opening/Closing으로 잡음 제거 → Contour → 병반 면적비 = 병반 픽셀 / 잎 픽셀, 반점 개수
→ ResNet18 top1.label·score와 비교 → 둘이 어긋나면 "확인 필요" 표시
```

| 방법 | 노리는 문제 (이번 관찰과 연결) | 주의점 |
|---|---|---|
| HSV 병반 면적비 | `healthy_test.10`을 bean_rust로 판정한 사례: 면적비가 낮으면 "확인 필요"로 표시 | 흙·그림자·햇빛에 따라 색 임계값이 변함. 사진 배경에 갈색 흙이 많음 |
| 잎 ROI·GrabCut 마스크 | 배경(흙, 손)의 영향 줄이기. 실제로 배경에 흙·손가락이 찍힌 사진이 있음 | 마스크가 실패하면 잎 정보까지 잘려 나감 |
| Contour 반점 개수·크기 | angular_leaf_spot(각진 큰 반점)과 bean_rust(작은 점 여러 개) 구분 보조 | 반점 모양 기준은 Train으로만 정함 |
| Grad-CAM 히트맵 | 모델이 잎을 보는지 배경을 보는지 확인 | **히트맵 자체는 성능을 올리지 않음** (설명용) |
| 규칙 기반 보류 | top1 score < 기준값이거나 면적비와 충돌하면 `review_required` | 라벨을 강제로 바꾸지 않음. 기본 API에 없는 확장 필드 |
| CNN 점수 + HSV 통계 → LogisticRegression | 두 병해 혼동 보완 (B 모델 Test에서도 bean_rust → angular 4장으로 가장 큰 오류) | Train 안에서 교차검증으로 특징을 만들어야 데이터 누출이 없음 |

**규칙 판단 예시 (수치는 모두 가상 설계값이며 검증하지 않았다)**

| 조건 | AI 예측 | OpenCV 관찰 | 최종 제안 |
|---|---|---|---|
| A | healthy, 0.97 | 병반 면적비 0.01 | AI 결과 유지 |
| B | healthy, 0.54 | 병반 면적비 0.25 | 확인 필요 |
| C | angular_leaf_spot, 0.46 | 큰 반점 2개 | AI 결과 유지 + 확인 권장 |

**검증 계획:** 임계값은 Train으로 정하고 → Validation으로 비교·선택하고 → 확정한 뒤 Test에서 **한 번만** 확인한다. CNN 단독 성능과 후처리를 포함한 시스템 성능은 따로 보고한다.

**우선순위 제안:** ① 서비스 모델을 B로 교체 검토 (Test 0.9531 확인됨, 교체하면 증빙을 다시 찍어야 함) → ② 오분류 사진 HSV 분석 → ③ 규칙 보류 → ④ 필요하면 ML 융합

## 9. 최종 판정과 한계

| 구분 | 결과 |
|---|---|
| 필수 기능 | ✅ 데이터 점검, Head-only 학습·저장, 동기 API, Redis 캐시 HIT/MISS, Celery 비동기 202 → done, PostgreSQL 기록, 응답시간 비교 — 모두 실제 실행 증빙 있음 |
| 선택 실험 | ✅ Full Fine-tuning 비교 (Validation 0.9699) |
| 선택 제안 | 📝 OpenCV·ML 융합은 설계만 (미구현) |
| 모델 분류 품질 | 서비스 모델 A: Validation 0.7669 (Test 미측정) / 최종 선택 모델 B: Validation 0.9699, **Test 0.9531** |

**한계**
- Test 지표는 B 모델만 1회 측정했다. 서비스 모델 A의 Test 지표는 **미측정**이다.
- 서비스에는 정확도가 더 낮은 A 모델이 연결돼 있다. 산출물 2~7 증빙의 일관성을 지키려고 바꾸지 않았다.
- 응답시간은 한 PC 안(127.0.0.1)에서 5회씩만 잰 값이다. 네트워크 지연과 동시 접속은 반영하지 않았다.
- 실패 경로(503, failed)는 실환경에서 확인하지 않았다.
- 데이터는 공개 Beans 데이터셋(데이터셋 페이지 표기 MIT, 모델 Apache-2.0)이다. 실제 밭의 조명·카메라에서의 성능은 보장하지 않는다.

**추후 과제:** 서비스 모델을 B로 교체한 뒤 증빙 갱신 → 서버 시작 시 모델 warm-up → bean_rust/angular 혼동 사진 HSV 분석 → 규칙 실험
