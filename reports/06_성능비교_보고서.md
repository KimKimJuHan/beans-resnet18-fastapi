## 3. 비동기 1회차 이상값 (콜드스타트)

- 비동기 MISS 1회차의 `inference_ms` 2624.61ms는 **Worker 프로세스가 모델을 처음 불러온 시간**이 섞인 값이다.
  - 측정 직전에 Worker를 재시작했다 (T-10 테스트). 그 뒤 첫 작업(job 3)은 캐시 HIT이라 모델을 불러오지 않았다. 그래서 측정의 첫 MISS(job 4)에서 처음 로딩이 일어났다.
  - `services.py`는 `get_classifier()` 호출을 타이머 안에서 실행한다. 모델은 `lru_cache`로 첫 호출 때만 불러온다. 앞선 job 2(3059.36ms)도 같은 현상이다.
- 1회차를 뺀 4회 중앙값: 최종 **221.7ms** (변화 없음), 추론 **18.31ms**. 중앙값이라 이상값 1개의 영향은 작았다.
- **결론: 모델 첫 로딩은 프로세스마다 2.6~3.1초가 걸린다.** 측정할 때는 워밍업으로 따로 빼야 한다.

## 4. 계산

```text
HTTP 응답시간 감소율 (동기 MISS 결과 응답 → 비동기 MISS 접수 응답)
  = (20.2 - 12.3) / 20.2 × 100 = 39.1%

결과를 받기까지 걸린 시간 차이 (비동기 MISS 최종 - 동기 MISS)
  = 221.7 - 20.2 = 201.5 ms   → 비동기가 더 느림

동기 캐시 효과 (MISS → HIT HTTP)
  = (20.2 - 1.5) / 20.2 × 100 = 92.6% 감소
```

## 6. 해석

1. **비동기 접수 응답은 동기 결과 응답보다 39.1% 빨랐다** (20.2 → 12.3ms). 이건 모델 추론이 빨라졌다는 뜻이 **아니다.** 접수와 처리를 나눈 효과다. 이 환경에서는 추론 자체가 16ms 정도로 짧아서 차이가 7.9ms에 그쳤다. 추론이 길어질수록 이 효과는 커진다.
2. **결과를 받기까지는 비동기가 약 200ms 더 느렸다.** 비동기 최종 시간이 MISS(221.7)와 HIT(220.6)에서 거의 같다. 즉 이 시간의 대부분은 **상태조회 간격 0.2초**와 큐 전달 시간이다. 추론 시간이 아니다. 브라우저 화면은 1초 간격으로 조회해서 1077ms가 나왔다 (`async_done_hit.png`).
3. **캐시 HIT은 동기에서 효과가 컸다** (20.2 → 1.5ms). 비동기에서는 접수 시간이 거의 같고, 최종 시간은 폴링 간격에 묻혀서 차이가 드러나지 않았다.
4. 같은 CPU 모델이라도 FastAPI에서 잰 추론 중앙값(16.18)과 Worker에서 잰 값(18.96)은 조금 다르다. 프로세스가 다르고 반복 수가 5회뿐이라, 이 차이에 의미를 두지 않는다.
